# 微信登录接入说明（H5）

> 结论先说：**入口只有一个 —— 用微信打开 H5，落在首页。扫码进来的第一屏不做任何登录。**
>
> 登录被拆成两件互不打扰的事：
> - **登录 = 只要能「认人」的标识（openid）**。微信内用 `snsapi_base` **静默授权**（微信侧不弹授权页、不问昵称头像），
>   用户点「立即预约」时先弹一张**我们自己的授权确认卡**（讲清只拿 openid、不拿昵称头像），点「允许」才跳一圈回来登录；
>   微信外（普通浏览器）发不了网页授权，**只给扫码引导**：页面显示二维码 + 可复制的链接，把用户送回微信里登录。
>   浏览器里**不提供第二条登录通道**——原因见 A1「为什么不在浏览器里登录」。
> - **个人信息（昵称 / 头像）≠ 登录**。它由用户自己在「我的 → 头像与昵称」里点一下主动触发
>   `snsapi_userinfo` 授权，**这一档才会真弹微信自己的「是否允许获取你的昵称、头像」**，拿到后回填到账号上。
>
> 一句话：**不该为了登录逼用户同意「获取昵称头像」**，身份和资料是两次授权、两套接口。

本文分两部分：
- **A. H5 侧已实现的内容**（本次交付，可直接跑）
- **B. 其它地方要做什么**（微信资质、后端接口、部署运维）——H5 仓范围之外，但缺一件就跑不起来

## A. H5 侧实现

### A1. 用户看到的流程

```
运营物料上的二维码
        │  微信扫码（或普通浏览器打开）
        ▼
   首页（可匿名浏览，不登录、不弹任何授权）
        │
        │  用户点「立即预约表演」—— 这是第一次需要身份的动作
        ▼
   我们自己弹的「微信授权确认」卡（应用名 / 拿什么 / 不拿什么 / 拒绝 · 允许）
        │
   ┌────┴─ 点「拒绝」→ 卡片关闭，什么都不发生（不留痕、不跳转），停在首页
   │
   └─ 点「允许」→ 才真正发起授权
        │
   ┌─ 微信内（能调起微信接口）──────────────┐   ┌─ 微信外（普通浏览器）─────────────────┐
   │ snsapi_base 静默授权（微信不弹窗）      │   │ 只给扫码引导：二维码 + 可复制链接      │
   │ 跳一圈回来 → 后端换 openid → token      │   │ 用户回微信里打开 → 再走左边这条        │
   └────────────────┬──────────────────────┘   └──────────────────────────────────────┘
                    │ 登录成功（只写 token + 基础 user）
                    ▼
                    回到「预约须知」页继续填，用户全程不用同意任何「获取资料」

   之后（可选、由用户自己发起）：
   「我的」→ 头像与昵称 → 「用微信资料填充」→ 先弹资料确认卡 → 允许
        → snsapi_userinfo 真弹微信授权页 → 允许 → 昵称头像回填
```

要点：
- **扫码进来就是首页，不做任何登录**；匿名可以浏览全部内容，只有真正要下单/看订单/进「我的」时才要身份。
- **登录时机 = 用户点了一个需要身份的动作**，既不是页面一加载、也不是扫码瞬间。
- **授权确认卡是我们自己写的**（`components/WxAuthSheet.vue`），不是微信弹的：`snsapi_base` 在微信侧
  静默无弹窗，用户点完预约只会看到页面闪一下，容易以为没反应。所以先由我们讲清「拿什么 / 不拿什么」，
  用户点「允许」才跳转；点「拒绝」就留在原地。这也顺带满足了微信「必须有用户交互才能跳授权」的要求。
- **浏览器里没有登录通道**：微信外只展示扫码引导。三条路径（微信内静默授权 / 扫码回到微信 /
  演示环境的手机号）登录成功后的收尾完全一致（`setLogin(token, user)` + `jumpAfterLogin(redirect)`），
  页面侧不区分用户是怎么登进来的。
- **静默授权不是「随便拿人资料」**：`snsapi_base` 只返回 openid，微信侧不会有任何弹窗，
  也拿不到昵称头像——这正是「登录只要必需信息」的落地方式。
- **昵称头像是独立的一次授权**：用户在「我的 → 头像与昵称 → 用微信资料填充」，先看到我们的资料确认卡，
  点「允许」后才是微信自己统一渲染的「是否允许 获取你的昵称、头像」。不点就一直只有 openid，不影响下单。
- **不会出现「页面一加载就跳授权」**：微信会把无用户交互的自动跳转固化成快照页（只显示「点击访问完整网页」）。
  现在所有跳转都由确认卡上的「允许」点击触发，深链直接进预约页也是先弹卡。
- 手机号通道（**仅演示环境**）：60s 重发倒计时；演示/Mock 环境验证码固定为 `123456`
  （由接口返回 `demoCode` 决定是否提示，真实后端不返回即不提示）。正式环境登录页不出现该入口。

### A1.1 为什么不在浏览器里登录（账号唯一化）

这是**产品规则**，不只是技术选择：

1. **浏览器里发不了微信网页授权**（微信硬限制：只能在微信内置浏览器发起）。想在浏览器里登录只有两条路：
   手机号验证码，或微信开放平台「网站应用扫码登录」——后者要另申请资质、另一套 AppID，
   且和公众号的 openid 不互通（只能靠 unionid 关联），本轮没做。
2. **手机号登录的代价是两个账号**。同一真人会变成「微信 half 账号（只有 openid）」+「手机号 half 账号」。
   服务端的「进行中咨询单唯一」是**按账号**判的，两个账号就各自能建一单 → 两份本地草稿、两张进行中的单；
   合并时还要把订单迁过去、把另一端会话重指向，否则用户会看到「我那一单不见了」。
3. **自动关联在这里做不到**。想让「一端登过、另一端登录时自动关联」，得在另一端拿到同一个微信标识——
   浏览器里拿不到（无法授权）；而微信内（X5 内核）与系统浏览器的 localStorage 是两个存储环境，
   「本机记住上次 openid」传不过去。所以没有可靠的自动关联，只能靠显式绑定（「我的」里的绑定手机号/绑定微信）。
4. **收敛后的规则**：正式环境只保留微信一条登录入口，浏览器端只负责把用户送回微信。
   账号唯一 → 一个真人一个账号 → 草稿与进行中单天然唯一。
   （历史数据或演示环境仍可能存在两个「半个账号」，绑定/合并逻辑保留，见 B2.1。）

| `src/services/auth.ts` | 编排唯一入口：`beginLogin`（登录，base 静默）/ `requireLogin` / `beginProfileAuth`（资料，userinfo 弹授权）/ `completeMockLogin` / `resumeFromCallback`（按 intent 分派）/ `initAuth` / `logout`；手机号通道 `sendSmsCode` / `loginWithSms` / `isValidPhone` |

| `src/components/WxAuthSheet.vue` | 我们自己写的授权确认卡（应用名 + 这次拿什么/不拿什么 + 拒绝/允许）；挂在需要登录的页面模板里（首页、预约、我的、咨询、订单等 7 个页面） |

| `src/config/env.ts` | 微信相关配置唯一出口（业务代码不直接读 `import.meta.env`） |
| `src/pages/login/login.vue` | 微信外是**扫码引导**（二维码 + 复制链接，正式环境唯一形态）；微信内是兜底界面（静默登录失败/手动访问时才看到）；手机号验证码仅在 mock 下可切（演示用） |
| `src/pages/user/index.vue` | 「我的」：登录态展示 + **微信资料主动授权入口** |
| `src/App.vue` | `onLaunch` 调 `initAuth()`：恢复登录态 + 处理微信回跳 `?code=&state=` |
| `src/utils/request.ts` | 401 统一清登录态并带去登录页（不做编排，避免循环依赖） |
| `src/mock/router.ts` | Mock 的 `/auth/wechat-login`（模拟 code2session + 建档）、`/user/wechat-profile`（模拟取昵称头像）、`/auth/sms/code`、`/auth/sms/login`、`/auth/me`、`/auth/logout` |

登录门调用方式（页面统一用它，不要自己写跳登录页）：

```ts
import { requireLogin } from '@/services/auth'

// 任何入口都一样：未登录会先弹「微信授权确认」卡，用户点「允许」才跳转
if (!requireLogin('/pages/apply/venue')) return

// 页面 onLoad 兜底（深链直接进来）：同样是先弹卡，不会出现「加载即跳授权」的快照页
requireLogin('/pages/apply/venue')

// 登录页自己已经是登录 UI（用户点过「微信登录」按钮），不再叠一层确认卡
beginLogin(redirect, { confirm: false })
```

**挂载约定**：能触发登录的页面模板里都要放一行 `<WxAuthSheet />`（放在页面根容器内）。
漏了也不会致命——`wxAuthSheet` 检测到没有挂载时会退化成 `uni.showModal`，
但那就不是设计好的卡片了，所以新增登录入口时要顺手挂上。

### A3. 配置项

`src/config/env.ts` 读取，值放在 `.env` 分层里：

| 变量 | 说明 | 默认 |
| --- | --- | --- |
| `VITE_WX_AUTH_MODE` | `mock`（本地模拟授权）/ `real`（真实微信授权） | `.env` 里是 `mock`，`.env.production` 里是 `real` |
| `VITE_WX_APP_ID` | 服务号 AppID（公开标识，**不是密钥**，可入库） | 空 |
| `VITE_WX_SCOPE` | **登录**用的作用域：`snsapi_base`（默认，静默无弹窗、只拿 openid）/ `snsapi_userinfo`（登录时就弹授权页顺手拿资料） | `snsapi_base` |
| `VITE_WX_REDIRECT_URI` | 授权回调基址，必须在公众平台「网页授权域名」下；空则取站点根目录 | 空 |

「我的 → 微信资料」那次授权**固定用 `snsapi_userinfo`**（写死在 `auth.ts` 的 `PROFILE_SCOPE`），
不受 `VITE_WX_SCOPE` 影响——登录和资料是两个用途，不能混在一个开关上。

**AppSecret 绝对不能进前端**（不带 `VITE_` 前缀也会被构建进产物，所以根本不要放），只能在后端环境变量里。

降级规则：`real` 模式但 `VITE_WX_APP_ID` 为空时，前端自动降级为 `mock` 并 `console.warn` —— 避免跳到必然报错的授权链接。

### A4. 两种模式怎么用

- **mock（默认，开发/演示/自动化）**：不需要任何微信资质。微信内点「立即预约」先弹我们自己的
  授权确认卡，点「允许」后**模拟静默登录**（不经过登录页），与真实链路的用户感知一致；
  微信外展示**扫码引导**，并额外保留一个「演示用：使用手机号登录」入口（不掏手机也能跑完流程）。
  `node .shots-tmp/h5-login-e2e.mjs` 覆盖 36 个断言（含「先弹卡再跳转」「拒绝不留痕」
  「允许后静默登录不进登录页」「浏览器里只有扫码引导」「我的里主动取资料也要先弹卡」）。
- **real**：真实跳转微信授权。需要 A3 里的 AppID + 公众平台网页授权域名；
  **微信外只给扫码引导，没有手机号入口**。
  `node .shots-tmp/h5-login-real-e2e.mjs` 在不连真实微信的前提下校验协议链路（授权 URL 参数顺序/编码、
  state 校验、伪造 state 拒绝、回跳换 token、回跳目标页、微信外引导）。
- **手机号验证码（仅演示环境）**：不依赖任何微信资质，**正式环境不开放**——它是能绕过微信另建账号的口子。
  Mock 下发码后提示「演示验证码 123456」（由接口返回 `demoCode` 决定），真实后端接短信服务商后即为真实短信；
  同一套 e2e 覆盖了发码、登录、错误验证码、深链登录回跳。

### A5. 关键实现细节（改动前务必知道）

1. **授权链接参数顺序不能改**：`appid → redirect_uri → response_type → scope → state → #wechat_redirect`，
   微信对链接做正则强匹配校验，顺序错了授权页直接打不开。
2. **`state` 只放随机串**（`[a-zA-Z0-9]`，24 位）。官方限制 state ≤128 字节且只能用字母数字，
   所以「登录后回哪一页」不能塞进 state，单独存 `sessionStorage`，回跳时用 state 校验来源再取回目标。
3. **`redirect_uri` 用站点根目录**（`location.origin + 目录/`），不带 hash。
   这样微信把 `?code=&state=` 拼在 `?` 后，解析没有歧义；应用内路由靠 `uni.reLaunch` 回跳。
4. **`code` 一次性、5 分钟过期**：回跳时先清地址栏再换 token，避免刷新/分享导致二次使用。
5. **换 token 必须走后端**：前端拿 code 调 `POST /api/auth/wechat-login`，AppSecret 只在服务端。
6. **401 处理**：`request.ts` 清 storage + 内存登录态，跳登录页（登录页自己再按环境决定是跳授权还是提示扫码），
   且已在登录页时不再重复跳转，避免死循环。
7. **一次授权往返只干一件事（intent）**：`sessionStorage` 里另存 `wx_oauth_intent`（`login` / `profile`）。
   回跳后 `resumeFromCallback` 按它分派：`login` → `POST /auth/wechat-login` 换 token；
   `profile` → `POST /user/wechat-profile` 只回填昵称头像、不动 token。两者共用同一套 state 校验，互不串味。
8. **两个 scope 不能混用**：`snsapi_base` 只回 openid（静默、无弹窗）→ 用于**登录**；
   `snsapi_userinfo` 才回昵称头像（有授权弹窗）→ 用于**「我的」里主动取资料**。
   用错后果很具体：拿 userinfo 去登录 = 用户每次登录都要点一次「允许」；拿 base 去取资料 = 永远取不到昵称头像。
9. **资料可能一直是空的**：登录后 `user.profileReady` 为 `false`，昵称是后端给的中性占位（如「微信用户_0001」），
   头像是默认图。页面**不能**把空的昵称头像当成异常，也不要在登录后自动去要资料——那是用户主动行为。
10. **确认卡同时解决两件事**：`snsapi_base` 在微信侧静默，所以「让用户看见自己在授权」只能我们自己提供；
   而微信又要求跳授权前必须有用户交互（否则固化成快照页）。卡片上的「允许」既是告知，也是那次交互。
   因此 `beginLogin` 内部改成了 async，但**调用点一律不 await**：`requireLogin` 仍返回 `false`
   表示「正在登录，调用方先 return」，页面逻辑不受影响。
11. **一个 intent 一次确认**：卡片同一时刻只服务一个待确认的请求（连点不会叠出两张卡），
   组件全卸载时悬着的 Promise 会被判为「拒绝」，不会留下永远不 resolve 的流程。

## B. 其它地方要做什么（H5 仓之外）

### B1. 微信资质（不能跳过）

| 场景 | 要求 | 费用/周期 |
| --- | --- | --- |
| **本地/开发调试** | 微信公众平台**测试号**（`https://mp.weixin.qq.com/debug/cgi-bin/sandbox?t=sandbox/login` 微信扫码登录即得 AppID/AppSecret），在「网页服务-网页帐号-网页授权获取用户基本信息」里配置授权回调域名 | 免费、几分钟 |
| **正式上线** | **已认证的服务号**（企业/组织主体）+ 微信认证；个人订阅号不行，未认证服务号也不行 | 认证 300 元/年，审核 1–5 个工作日 |
| 域名 | 公众平台「设置与开发-账号设置-功能设置-网页授权域名」填写**全域名**（不带 `http://`），该域名下所有页面都能授权；微信要求回调建议用 **HTTPS** | 域名需已完成 ICP 备案（国内） |

要点：
- 网页授权是**服务号能力**；订阅号、未认证服务号、小程序、开放平台网站应用都不是这套流程
  （开放平台「网站应用扫码登录」是另一件事：电脑上显示二维码、手机扫码确认，本次没有做）。
- 授权域名只认**全域名**：配了 `h5.example.com` 就只有它能授权，`pay.h5.example.com`、`example.com` 都不行。

#### 测试号页面到底哪几格要填（实测 2026-11）

测试号管理页有 4 个可填区，**只有 1 个和网页授权登录有关**，别填错地方：

| 页面区块 | 登录是否需要 | 填什么 |
| --- | --- | --- |
| 测试号信息（`appID` / `appsecret`） | **必需** | `appID` 是公开标识，可进前端 `.env.local`；`appsecret` **只给后端**环境变量 |
| 「接口配置信息」URL / Token | 不需要 | 这是公众号消息推送（收消息/事件）的接入配置，留空即可 |
| 「JS接口安全域名」 | 不需要 | 这是 JSSDK（`wx.config`）用；以后要做自定义分享卡片才填，登录不依赖 |
| 「网页服务 → 网页帐号 → 网页授权获取用户基本信息 → 修改」 | **必需（关键项，在页面更下方）** | 填授权回调**全域名**，不带 `http://`、不带端口、不带路径 |

补充：
- 测试号填授权回调域名**即时生效，不需要上传 `MP_verify_*.txt` 校验文件**（正式服务号才需要）。
- 测试号页面上的 `appsecret` 若显示为星号/为空，说明已被隐藏，只能点旁边的「重置」生成新值；
  重置后旧值立即失效，前后端要同步换。
- 建议手机微信扫页面上的测试号二维码关注一下（部分场景报 10006 就是没关注）。

### B2. 后端接口（`drone-dispatch-server`，已实现）

> 这一节的接口 2026-11-20 已合并进 server 仓，实现见 `H5AuthController` / `H5UserController` / `H5AuthService`。
> 下文的契约是当初的设计草案，和落地版本有六处出入，读代码时以这里为准：
>
> - 用户端接口统一挂在 `/api/h5` 下，与管理端 `/api/auth` 的账号密码登录分开。下文出现的 `/api/auth/...`、
>   `/api/user/...` 都要加 `/h5` 前缀（例如 `POST /api/h5/auth/wechat-login`）。
> - 令牌是独立的用户令牌（claim `typ=user`，subject 是 `users.id`），由 `H5AuthInterceptor` 校验。
>   管理端令牌打用户端接口、用户端令牌打管理端接口都是 401 —— 两套身份域故意不通用（否则 `users.id`
>   撞 `admin_users.id` 就是越权）。
> - 成功码是 `200`，信封是 `{ code, message, data }`；H5 前端在 `request.ts` 里已归一成 `{ code: 0, msg }`，
>   页面代码不用改。
> - 配置键是 `app.wechat.*`（环境变量 `APP_WECHAT_ENABLED`、`WX_APP_ID`、`WX_APP_SECRET`、
>   `APP_WECHAT_API_BASE_URL`），不是 `app.wx.*`。
> - 合并只发生在 `bind-phone` / `bind-wechat` 里，且只认服务端验证过的身份；登录接口里客户端附带的
>   `phone` / `openid` 一律忽略（采信未经校验的客户端身份等于允许任意绑定他人账号），所以登录返回的
>   `merged` 恒为 false。
> - 影子账号机制落在 `users.merged_into` / `merged_at` 两列上，另见 server 仓 `docs/账号合并契约.md`。

H5 认两个契约（都是匿名可访问，需加入 `JwtAuthInterceptor` 白名单）。

**① 微信网页授权（登录，`snsapi_base`）**

```
POST /api/h5/auth/wechat-login
body: { "code": "<微信回跳的 code>" }

成功: { "code": 200, "data": { "token": "<JWT>", "merged": false,
        "user": { "id", "nickname", "avatar", "phone", "openid", "profileReady": false } } }
失败: 非 0 code + message（前端会 toast 提示并可重试）
```

**注意**：登录这条用的是 `snsapi_base` 的 code，**换不到昵称头像**。所以 `user.nickname` 必须是后端给的中性占位
（如 `微信用户_0001`，不要用 openid 明文），`profileReady` 固定 `false`——资料等用户在「我的」里主动授权后再回填。

**② 主动获取微信资料（`snsapi_userinfo`，需登录态）**

```
POST /api/h5/user/wechat-profile        (Authorization: Bearer <token>)
body: { "code": "<snsapi_userinfo 回跳的 code>" }

成功: { "code": 200, "data": { "nickname": "...", "avatar": "https://...", "openid": "..." } }
失败: 非 0 code + message
```

服务端拿到这个 code 后要调 `GET https://api.weixin.qq.com/sns/userinfo?access_token=&openid=&lang=zh_CN`
（注意：code 换来的 access_token 与 openid 是一次性的，别和 cgi-bin 的全局 token 混用），
再把昵称头像写回当前登录用户，并把 `profileReady` 置 `true`。前端会 `patchUser` 回填，不动 token。
实现里还加了一条校验：本次 code 换出的 openid 必须等于当前账号已绑的 openid，否则返回 40006 ——
防止拿别人的 code 把别人的昵称头像写进自己账号。

**③ 手机号验证码**（**仅演示环境**；正式环境登录页不展示该通道，接口保留供本地联调）

```
POST /api/h5/auth/sms/code
body: { "phone": "13800001111" }
成功: { "code": 200, "data": { "ttl": 300, "demoCode": "123456" } }   // demoCode 只在演示开关打开时出现
失败: 429（同号 60 秒内重发）

POST /api/h5/auth/sms/login
body: { "phone": "13800001111", "code": "123456" }
成功: { "code": 200, "data": { "token": "<JWT>", "merged": false,
        "user": { "id", "nickname", "avatar", "phone", "openid", "profileReady" } } }
失败: 非 0 code + message（验证码错误/过期/触发频控）
```

服务端要做的事：

1. **code2session**：`GET https://api.weixin.qq.com/sns/oauth2/access_token?appid=&secret=&code=&grant_type=authorization_code`
   → 拿 `openid` / `access_token` / `unionid`。**登录接口只走到这一步**（校验 + 建档 + 签发 token），不要再顺手调 userinfo。
2. **快照页账号必须拒绝**：返回里 `is_snapshotuser == 1` 表示是微信快照页虚拟账号，不能当真实用户登录。
3. **拉资料只在 `/user/wechat-profile` 里做**：`GET https://api.weixin.qq.com/sns/userinfo?access_token=&openid=&lang=zh_CN`
   → `nickname` / `headimgurl`，写回当前用户并置 `profileReady=true`。用户不主动点「微信资料」，后端就永远不拉。
   另：2022-10 起微信对未认证主体/部分场景下发的是**匿名昵称头像**（如「微信用户」+ 灰色默认头像），
   拿到这种值也要照常存，不要报错。
4. **建档**：`users` 表加 `openid`（唯一索引）、`unionid`（可空）、`avatar`、`nickname`；
   同一 openid 复用账号，首次登录自动建档。
5. **签发 JWT**：用户令牌带 claim `typ=user`、subject 是 `users.id`，由 `H5AuthInterceptor` 校验；管理端令牌不带这个 claim，两边拦截器互相拒绝对方的令牌。不要走「同一个拦截器按 role 放行」那条路——两套 id 空间撞号就是提权。
6. **配置**：`app.wechat.app-id`（可入库）、`app.wechat.app-secret`（**只**放环境变量 `WX_APP_SECRET`）；`app.wechat.enabled` 关着时微信登录返回明确的配置错误，不要 NPE。
7. **CORS**：`app.cors.allowed-origins` 已补 5174（H5 dev server 实际端口）；部署时按真实域名覆盖。
8. **安全**：发码限频（同号 60 秒）已实现，日志里 openid 脱敏，code 只消费一次。另外登录接口会忽略客户端带上来的身份字段，合并只认服务端验证过的手机号或 openid。
9. **授权撤销事件**（上线后建议）：订阅 `user_authorization_revoke` 消息推送，用户撤回昵称头像授权时清理本地缓存资料。
10. **短信接口**：接短信服务商（阿里云/腾讯云）；验证码 5 分钟有效、一次性消费；同号 60s 只能发一次、
    单号单日上限、按 IP 限流；日志脱敏手机号；`users.phone` 加唯一索引，同一手机号复用账号
    （与 openid 建档并存，二者合成一个账号的规则见 B2.1）。

#### B2.1 账号绑定与合并（微信身份 × 手机号身份）

正式收敛为「只微信登录」后，新账号不会再出现两个「半个账号」；但**历史数据与演示环境**里仍有
「微信里注册的只有 `openid`、浏览器里用手机号注册的只有 `phone`」的存量账号。
两边都可能各自下过单，所以**合并必须连订单一起搬**，否则用户会觉得「我那一单不见了」。
H5 已在「我的」页提供两个显式入口（当前账号缺哪个身份就显示哪个），后端需实现：

```
POST /api/user/bind-phone     { phone, code }        Authorization: Bearer <token>
POST /api/user/bind-wechat    { code }               Authorization: Bearer <token>

成功: { "code": 0, "data": { "user": {...}, "merged": true, "movedOrders": 1 } }
```

| 字段 | 说明 |
|---|---|
| `user` | 绑定/合并**之后**的账号；合并时 `id` 变成保留账号的 id，前端整体替换本地 user |
| `merged` | 本次是否把两个账号并成了一个 |
| `movedOrders` | 合并时迁过去的订单数，前端提示「已合并，N 笔订单已转入」 |

错误码：`40100` 未登录 / `40002` 手机号非法 / `40003` 缺验证码 / `40004` 验证码错或过期 /
`40005` 当前账号已有手机号（换号走客服）/ `40006` 当前账号已绑其他微信 / `40001` 缺授权 code。

合并规则（**一个事务**，漏任何一条都会出问题）：

1. **迁业务数据**：把被并掉那侧 `orders.user_id`、`reviews.user_id` 改挂到保留账号（当前 schema
   里就这两张；以后新增带 `user_id` 的表必须同步加进来）。合同/支付/退款通过 `order_id` 挂在
   订单下，订单迁了自动跟着走。
2. **迁身份位**：保留账号补上对方身份；被并侧 `openid` / `phone` 置 `NULL`（有唯一索引，两边都留会冲突）。
3. **软合并不删行**：被并侧写 `merged_into = 保留账号 id`、`merged_at`，留成「影子账号」供审计；
   物理删除会让历史订单变孤儿单。
4. **会话重指向**：被并侧未过期 token 重指到保留账号，别让另一端「突然被踢」。
5. **保留谁**：保留那个身份原本就挂着的账号（通常历史更多），把当前登录账号并进去。

补充两条实现注意：合并是**单向、不可逆**的（拆回要客服按审计记录人工处理），所以别提供
「解绑/拆分账号」的自动入口；两台设备同时发起绑定时要给 `users` 行加锁 + 幂等，
否则可能把同一个账号并两次（`merged_into` 成环）。

反例（`.tools/wx-server.js` 早期版本踩过）：只把身份位搬过去、`filter` 掉被并的账号行 ——
那笔订单 `user_id` 指向已不存在的 id，库里还在、用户「我的订单」里查不到，而且订单还在跑
（已接单/待服务），他付不了款也取消不了。完整的后端实现契约（含验收用例）见
`drone-dispatch-server/docs/账号合并契约.md`（该仓 `docs/` 按约定不入库，本机留存）。

### B3. 部署与联调

1. H5 部署到**已配置网页授权域名的 HTTPS 地址**（生产）。
2. 本地真机联调：微信必须能访问到回调地址 → 用内网穿透（cpolar / natapp / ngrok）把 `5174` 暴露成 HTTPS 域名，
   把这个域名填进测试号的授权回调域名，再把 `VITE_WX_REDIRECT_URI` 指向它。
3. 二维码：运营物料上的二维码指向 H5 URL 即可（可带来源参数）——那是**对外投放**的码，H5 不负责生成。
   登录页里的二维码是另一回事：它由前端现场生成（`qrcode` 包，内容 = 当前站点 + 登录页 + 目标页），
   只用于把浏览器里的用户送回微信，不对外投放、无需资质。
4. 用户协议 / 隐私政策：登录页已有入口占位，需补真实页面（合规要求，且微信审核会看）。

### B4. 可选：微信小程序端

工程里 `manifest.json` 已预留 `mp-weixin`。小程序不能走网页授权，要走：
`uni.login()` 拿 code → 后端 `jscode2session` 换 openid → 同样的 `{ token, user }` 契约。
H5 这轮的登录编排（`services/auth.ts`）已经按「登录流程集中一处」组织，小程序端接同一个服务层即可，
但**这轮没有实现也没有验证**。

## C. 排错对照表

### C0. 先验凭证，再看页面（省很多时间）

上线/联调前先确认 AppID 与 AppSecret 这一对是有效的（在服务器或本机执行）：

```bash
curl -s "https://api.weixin.qq.com/cgi-bin/token?grant_type=client_credential&appid=<APPID>&secret=<SECRET>"
# 有效：{"access_token":"...","expires_in":7200}
# 无效：{"errcode":40125,"errmsg":"invalid appsecret ..."}
```

**坑（实测）**：拿假 code 去调 `sns/oauth2/access_token`，返回的是 `40029 invalid code`，
即使 secret 是错的也一样（该接口先校验 appid、后校验 code，secret 校验更靠后）。
所以**不能用「返回 invalid code」反证 secret 正确**，判断凭证只能用上面的 `cgi-bin/token`。

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 授权页提示「该链接无法访问」/ 10003 | `redirect_uri` 与公众平台配置的授权域名不一致 | 检查域名（全域名匹配）、协议、端口 |
| 10005 | 账号没有 `snsapi_userinfo` 权限 | 用已认证服务号或测试号 |
| 10006 | 测试号要求先关注 | 关注测试号 / 配置体验者 |
| 10012 / 10011 | appid / redirect_uri 为空 | 检查 `.env` 与授权链接 |
| 微信里显示「点击访问完整网页」 | 页面加载后无交互直接跳授权 | 已处理：所有跳转都由确认卡上的「允许」点击触发（`beginLogin` 内部先 `askWxAuth`） |
| 登录后没回到原页面 | `redirect` 丢失 / 被清 | 检查 `sessionStorage` 的 `wx_oauth_redirect` 与 `beginLogin` 传参 |
| 一直循环跳登录页 | 401 反复触发 | 已处理：登录页不再重复跳转；后端需把 `/auth/wechat-login` 加白名单 |
| 微信里点「预约」弹了卡、但没有微信自己的授权页 | **预期行为**：登录用 `snsapi_base`，微信侧静默；那张卡是我们自己画的确认 | 想让微信也弹一次，把 `VITE_WX_SCOPE` 改成 `snsapi_userinfo` |
| 点「预约」弹窗样式很朴素、不像设计稿 | 该页面没挂 `<WxAuthSheet />`，退化成系统 `uni.showModal` | 在页面模板根容器内补一行 `<WxAuthSheet />` |
| 点确认卡「允许」后没有任何反应 | real 模式下 `redirect_uri` 不在网页授权域名下，微信直接拒绝 | 按上表检查域名/端口；本地真机联调用内网穿透 HTTPS 域名 |
| 登录后昵称是「微信用户_0001」、头像是默认图 | **预期行为**：登录不索取昵称头像 | 去「我的 → 微信资料」点一下，走 userinfo 授权后才会有 |
| 「我的 → 头像与昵称」里点「用微信资料填充」没反应 | 在微信外（浏览器）打开 | 网页授权只能在微信内置浏览器发起，页面会提示「请用微信打开」 |
| 普通浏览器点「登录/预约」只看到二维码 | **预期行为**：正式环境浏览器里没有登录通道 | 用手机微信扫码（或复制链接到微信里打开）继续；演示环境可切「手机号登录」 |
| 后端报 `40125 invalid appsecret` | 后端配的 AppSecret 与 AppID 不是一对，或已被重置失效 | 测试号页面点「重置」重新生成，只更新后端环境变量 `WX_APP_SECRET` |
| 后端报 `40029 invalid code` | code 用过一次、超过 5 分钟、或伪造 | code 只消费一次；刷新页面会失效，需重新走授权拿新 code |
| 后端报 `40013 invalid appid` | AppID 写错串 | 核对测试号页面顶部的 `appID`（32 位） |
| 后端报 `40164 invalid ip` | 调用来源 IP 不在白名单（正式服务号才有此限制） | 「设置与开发-基本配置-IP白名单」加服务器出口 IP；测试号无此限制 |
| `redirect_uri 参数错误` | 回调域名没配 / 配的和用的不是同一个 / 带了端口 | 测试号「网页授权获取用户基本信息」填同一个全域名，`VITE_WX_REDIRECT_URI` 与之完全一致 |
